PC platforms first (Windows, macOS, Linux); Android and iOS after.

Executive summary

Four real, popular, actively developed download managers were read at the code level to inform this design — not just their READMEs. Two are C#, one is Kotlin/Compose Multiplatform, one is Go/Flutter. Between them they demonstrate four different segmented-download algorithms, two different persistence philosophies, two different browser-integration mechanisms, and two very different approaches to "beautiful UI." None of the four is worth copying wholesale; each has at least one idea worth stealing and at least one thing worth deliberately not repeating.

The single most consequential finding: the most popular of the four (AB Download Manager, 194,000 lines, 17.7k stars) uses no SQL database at all — just atomic write-then-rename JSON files, one per download/queue/setting. That single choice, adopted here, sidesteps the exact System.Data.SQLite.Core-on-iOS blocker found while researching XDM's own mobile port in a companion document. It's simpler, dependency-free, human-debuggable, and entirely sufficient for the entity counts a download manager actually has.

Section 07 gives a direct Avalonia-vs-Uno recommendation, reasoned from what these four apps actually need rather than repeated from either of the two other verdicts already produced this session (for a Material-styled mobile app, and for XDM specifically). The answer here happens to agree with the XDM verdict — Avalonia — but for a distinct, app-specific reason: a from-scratch "cleaner, simpler" build benefits from Avalonia's smaller API surface and fully-flexible styling system more than from anything WinUI-specific, and this app has the same load-bearing tray-icon requirement XDM has.

Four chunking strategies, compared

Every one of the four solves "split one download across multiple connections" differently. None is wrong; they trade off simplicity against adaptiveness.

ProjectStrategyHow splits are decidedRebalancing
XDMSplit-largest-remainingA central coordinator (HTTPDownloaderBase.CreatePiece/FindMaxChunk) finds the piece with the most unfinished bytes and bisects it once >256KB remainsHappens centrally as connections free up
bezzad/DownloaderStatic equal-partitionChunkHub.Validate computes N equal-sized chunks once, upfront, from a configured chunk count and a minimum-size floorNone — fixed at start; only per-chunk retry
GopeedSlow-start + work-stealingStarts conservative, ramps connections up; a fast connection steals half the remaining work from a straggler (>3s from finishing, chunk ≥512KB)Continuous, live, between active connections
AB Download ManagerDynamic safe-zone splittingStarts with fewer threads than requested; splits the largest active part's tail on demand, gated by a "safe zone" (128×8192 bytes) so near-complete chunks aren't splitOn-demand as threads become free, safety-gated
Recommended synthesis: combine Gopeed's live work-stealing (the most effective answer to a straggler connection on an uneven server) with AB Download Manager's safe-zone gate (avoids wastefully re-splitting a chunk that's nearly done). In C#, implement this as an async coordinator over a small set of Channel<T>-based worker tasks rather than the hand-rolled locks both Kotlin and Go versions needed — see section 10.
04

Persistence: skip the database

Two of the four reference apps reach for a real database; two don't. The ones that don't have a real advantage for this project's mobile ambitions.

XDM

System.Data.SQLite.Core for download history. Confirmed, in a companion document, to depend on dlopen — which iOS blocks outright. A real migration cost if this app ever wants iOS.

AB Download Manager

No database anywhere. TransactionalFileSaver writes a .tmp file then atomically renames it over the real one — crash-safe, human-readable, dependency-free. Settings go through a typed schema layer over androidx.datastore with automatic default-fallback on corruption.

Recommendation: adopt AB Download Manager's approach wholesale. A download manager's entity counts — downloads, queues, settings, extension manifests — are in the hundreds at most, never the millions a real database earns its keep at. Atomic write-then-rename JSON, one file per entity, in a well-known app-data folder, avoids a SQLite-provider decision (and its iOS complications) entirely, and keeps every persisted file inspectable with a text editor during development.
05

Integration architecture

How the app talks to browser extensions, and how its own UI talks to its own engine, turn out to be the same architectural question — and only one of the four references answers it well.

Gopeed's protocol-agnostic dispatcher

Adopt

Gopeed defines its entire API surface once, as a route table of (Context) → Response handlers (pkg/api/service.go), completely independent of transport. Its real HTTP server (pkg/rest) is just one consumer of that table. Desktop and mobile builds skip HTTP entirely and call the same dispatcher in-process — via Dart FFI on desktop, via a gomobile-compiled binding on Android/iOS — converging on one shared function, rest.Invoke(method, path, query, body).

Why this matters more for a C# app than it did for Gopeed: Gopeed pays a real tax for this — a cgo/gomobile cross-compilation step and an FFI boundary between Go and Dart. A pure C#/.NET app doesn't need any of that: the "engine" is just a class library, referenced directly by an Avalonia desktop project, an Avalonia/Uno Android project, or an Avalonia/Uno iOS project, with zero IPC, zero serialization, and zero FFI. The dispatcher pattern is still worth keeping — it's what makes "also expose this over real HTTP for the browser extension" a clean addition instead of a parallel reimplementation — but the in-process path is even simpler here than it was for Gopeed.

AB Download Manager's real native-messaging support

Adopt

Unlike XDM (which leans on a loopback HTTP server the extension calls via fetch, with real native-messaging manifests present but appearing vestigial), AB Download Manager implements the actual Chrome/Firefox native-messaging stdio protocol (NativeMessagingHost.kt, StdioProtocol.kt) as its primary path, with a local Ktor HTTP server as a secondary/legacy option. The browser launches a short-lived host process that forwards to the already-running app via internal IPC.

This avoids the self-signed-port/CORS friction a pure-HTTP approach invites, and is the mechanism Chrome and Firefox actually document for this use case. Build this as the primary path from day one; keep an optional local HTTP endpoint (reusing the same dispatcher from above) for anything that genuinely needs it (a remote web UI, MCP/AI-agent tooling, in Gopeed's spirit).

What this rules out: XDM's "iOS as a remote-control client" idea, floated in the companion document as a way past its ffmpeg/SQLite blockers, is worth remembering as an option but not a default. Gopeed's own history is a caution here — it used to route local calls over loopback sockets and deliberately moved away from that. Default to in-process calls on every platform where the engine is compiled into the app; reserve a real network listener for cases that are genuinely cross-process (the browser extension) or genuinely remote (a self-hosted server, if ever built).
06

UI & "most beautiful" design

The brief calls for the most beautiful UI of the category. Neither of the two most polished references got there by using their platform's default design system unmodified.

Custom, not stock, theming

AB Download Manager explicitly does not use Material 3 — a fully custom palette/shape/ripple system (DefaultThemes.kt, ABDownloaderTheme.kt), with animated cross-fades between light/dark/custom themes rather than hard color cuts.

UI scale independent of the OS

A user-adjustable UI scale factor, applied uniformly across Windows/Linux/macOS instead of relying purely on OS-level DPI scaling — a small but distinctive polish detail worth reusing.

Clean Component/Page separation

Each of AB Download Manager's ~19 screens splits state/logic (a Component) from pure rendering (a Page) — the same shape as a ViewModel/View split, scaling to many screens without any one becoming a god-object.

Bespoke, not generic, data views

The download queue list is a hand-built sortable/reorderable table, not a stock data-grid control — worth the extra effort for the screen users spend the most time looking at.

What this means for the framework choice: a from-scratch, fully custom design system doesn't lean on either Avalonia's community Material theme or Uno's first-party Material/Fluent/Cupertino themes very much — both frameworks' styling systems are flexible enough to build a bespoke look on. This neutralizes what was a real point in Uno's favor for a different (Material-styled) app in this document series; it isn't a factor here. See section 07.
07

Avalonia vs Uno — the verdict, for this app

Reasoned fresh from this app's actual requirements, not carried over from either other verdict produced this session.

DimensionAvalonia UIUno Platform
System tray iconNative, documented TrayIcon — Windows, macOS, some LinuxOpen, unimplemented feature request (same gap found researching XDM)
Custom design system fitSmaller, less opinionated XAML dialect — less to override to get a fully custom, non-Fluent lookFull WinUI 3 surface, which leans Fluent by default; achievable but more to work against
"Cleaner, simpler" fitMatches the stated goal directly — a lighter API surface with less legacy WinUI baggageLarger surface; more powerful, but more than a from-scratch "simpler" build needs

Recommendation: Avalonia UI

Two reasons, both specific to this app rather than inherited from elsewhere in this document series. First, the same tray-icon gap found while researching XDM applies here too — a download manager that can't minimize to the tray is a real, user-visible regression from every reference app studied (XDM and AB Download Manager both implement it), and only Avalonia has a working answer today.

Second, and specific to this project: the explicit design goal is "cleaner, simpler... yet high performance," and a fully custom, non-Material, non-Fluent visual identity (section 06) is the plan. Avalonia's smaller, less historically-encumbered XAML dialect is less work to bend into a bespoke look than WinUI's larger, more opinionated surface — the same reasoning AB Download Manager's own team applied when they chose not to build on stock Material.

Bottom line: build the PC-first phase on Avalonia. Revisit only if Uno ships tray icon support, or if the mobile phase's specific needs (section 11) surface a reason strong enough to outweigh the above.

10

Do this / avoid this

Distilled directly from what worked and what didn't across all four codebases.

Do this

  • Zero-UI-dependency engine library (all four references that got this right scale better)
  • Work-stealing rebalancing over static upfront chunking (Gopeed + AB Download Manager)
  • Atomic write-then-rename JSON, no database (AB Download Manager)
  • One dispatcher, multiple transports — in-process for the UI, real HTTP only for the browser extension (Gopeed)
  • Real native-messaging protocol, not just a loopback server (AB Download Manager)
  • A typed settings schema with default-fallback on corruption (AB Download Manager)
  • Issue-driven regression tests, named after the bug they fix (bezzad/Downloader's Issue226Test.cs pattern)
  • Constant-time comparison for any API auth tokens (Gopeed)

Avoid this

  • Mixing coroutine/async retry loops with raw spawned threads (AB Download Manager's PartDownloader) — C#'s Stream.ReadAsync + CancellationToken needs no such workaround
  • Fine-grained manual locks spread across multiple objects per download job — consolidate around one coordinator per job (a Channel<T>-based actor, not scattered lock/Mutex)
  • Global mutable package-level state (Gopeed's Go singletons) — use constructor-injected singletons via Microsoft.Extensions.DependencyInjection instead
  • Loopback-HTTP-only browser integration with a vestigial, unused native-messaging path left half-built (XDM's current state)
  • A SQL database sized for a problem this small (XDM's System.Data.SQLite.Core, and its iOS consequences)
  • An FFI/cross-language boundary between engine and UI — unnecessary when everything is already C#

12

Open decisions

Adapt bezzad/Downloader, or write a new engine inspired by it?

Its MIT license permits either. Adapting directly saves real time (5,782 lines, already .NET 10-ready, AOT-compatible) but its static chunking (section 03) needs the work-stealing layer added on top either way.

Is BitTorrent in scope for v1?

Gopeed's popularity is partly built on BT support. If yes, budget for MonoTorrent integration in the roadmap; if v1 is HTTP/HTTPS-only, note that as a deliberate scope cut, not an oversight.

Video-site downloading (HLS/DASH), like XDM?

A real feature differentiator XDM has and the other three references vary on — decide before Phase 0, since it affects whether ffmpeg becomes a dependency at all (and therefore whether the iOS phase stays as clean as roadmapped in Phase 6).

Project name and license?

Not yet decided in this conversation — needed before Phase 0's repository exists for real.
