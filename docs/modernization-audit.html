00

Executive summary

The app is a six-screen, single-module Android project — a splash screen, a main menu, a 12-course catalog, a course-detail popup, a bundled PDF viewer, and a registration form. It was last touched around 2021 and has not been rebuilt since; several of the pieces it depends on to compile no longer exist.

It will not build in a current Android Studio for two independent reasons: the root build.gradle still points at JCenter, which shut down for good in February 2022, and it pins buildToolsVersion "30.0.3" alongside compileSdkVersion 33 using an Android Gradle Plugin (7.4.1) and Gradle (7.5) that both predate the JDK versions modern Android Studio ships with. None of this is a code problem — it's a toolchain that stopped being resolvable out from under the project.

Two of the eight third-party libraries in use (com.daimajia.androidanimations, com.orhanobut:dialogplus) were published to that same dead JCenter and are now permanently unresolvable at their pinned versions; a third (com.github.barteksc:android-pdf-viewer) has been unmaintained since roughly 2020 and its com.github.* coordinate needs a JitPack repository this project never declared in the first place. All three need to be replaced, not upgraded.

Underneath the build problems, the registration screen — the app's only feature that talks to a network — sends full personally identifiable information (name, birth date, blood group, phone numbers, home address) as a $-delimited string over a raw, unencrypted, unauthenticated WebSocket to a hardcoded LAN address, with no INTERNET permission even declared in the manifest and no server for it to reach anywhere in this repository. It was almost certainly a developer's local test rig that shipped by accident. Modernizing this screen means finally deciding what "Register" should actually do — see Open decisions.

The constraint that shapes every recommendation in this document: keep the look, feel, feature set, and logic identical. Every version bump, replacement library, and architectural change below is chosen because it can reproduce today's screens pixel-for-pixel and today's flows step-for-step — only what the app is built and secured with changes. Where a change is genuinely user-visible (fixing the broken BBA syllabus links, for instance), it's called out explicitly.

This document is the analysis and plan only — nothing in the repository has been changed. Section 15 lays out a phased, risk-ordered path from "fix the build" through "modern toolchain" to "cleaned-up architecture," each phase scoped so it can be verified against the current app before moving to the next.

Findings below carry a severity chip and, where applicable, a File.java:line citation pointing at the exact code read to produce this report at commit 41baa66.

Critical

Blocks the build outright, or breaks a core feature / security guarantee right now, on the app as it sits in this repo today.

High

Medium

Correct today, but deprecated, fragile, or actively working against you the moment the OS or toolchain moves — which is exactly what this project needs to do.

This is the one screen with a real backend ambition, and the one place where "keep the logic identical" runs headfirst into "the logic never actually worked."

Fig. 3 — the registration submit path, end to end. Every step is a real call in Registration.java.

The wire format has no escaping

Medium

Nineteen fields are joined with a literal "$" and sent as one string. Nothing checks whether a field itself contains $ — an address, a course name, or a name with a nickname in it will desynchronize every field after it on whatever eventually parses this.

mySendString = fName.getText().toString() + "$" +
               mName.getText().toString() + "$" +
               lName.getText().toString() + "$" +
    /* ... sixteen more fields, same pattern ... */
webSocket.send(mySendString);

Registration.java:184-211

Success is reported unconditionally

High

The accept button calls sendDataToSever() (note the typo) and, on the very next line, shows a "success" Toast and navigates back — with no wait for, or check of, any acknowledgement. SocketListener overrides all six WebSocketListener callbacks (Registration.java:215-251) but every one of them is an empty pass-through to super. A user is told they're registered even when the socket never opened.

Nothing on the other end

Critical

The target is ws://192.168.2.5:9999 — a private LAN address hardcoded at Registration.java:46,258. A repository-wide search turns up no server, no protocol spec, and no reference to this address anywhere else. This reads as a developer's local test rig against their own machine, not an endpoint that was ever meant to reach production.

06

Why it won't build today

Three independent, confirmed root causes — each verified by reading the actual build files in this repo, not inferred.

JCenter is gone

Critical

build.gradle:3-6,16-19 lists google() and jcenter() as the only two repositories, for both the buildscript classpath and every module. JCenter has been shut down and read-only since February 2022; many artifacts hosted there, including the exact daimajia and orhanobut coordinates this project pins, have since disappeared entirely. Any fresh ./gradlew sync fails to resolve them.

A JitPack-shaped dependency with no JitPack repository

High

com.github.barteksc:android-pdf-viewer uses the com.github.* group id convention specific to JitPack, but neither settings.gradle nor build.gradle declares maven { url 'https://jitpack.io' } anywhere in this repository. This dependency was likely resolving from a local Gradle cache during development and was never fully portable in the first place.

Toolchain pins predate the JDKs modern Android Studio bundles

Critical

app/build.gradle:6-7 pins compileSdkVersion 33 next to an explicit buildToolsVersion "30.0.3" — a Build Tools revision a current Android Studio install may not have available, and one that's no longer necessary to pin at all (AGP has auto-selected the correct Build Tools since AGP 4.x). Paired with AGP 7.4.1 and Gradle 7.5 (gradle-wrapper.properties:6), this whole stack sits roughly two years behind what current Android Studio, and Google Play's own submission requirements, expect.

07

Confirmed functional bugs

Everything here was verified directly against the source — not stylistic opinions, but places where the app's own behavior contradicts its intent.

BBA syllabus PDFs point at files that don't exist

High

The BBA course entry references three PDFs that are never actually bundled:

// Courses.java:119-122
showCoursePopup(v,"BBA - Bachelor of\nBusiness Administration", ...
    ,"cbcs_bba_fy.pdf","cbcs_bba_sy.pdf","cbcs_bba_ty.pdf");

The actual files in app/src/main/assets/ are named bba_fy.pdf, bba_sy.pdf, bba_ty.pdf — no cbcs_ prefix, unlike every other course's PDFs. All three BBA syllabus buttons silently fail to load.

Registration cannot function as shipped

Critical

AndroidManifest.xml declares zero <uses-permission> elements — not even INTERNET — yet Registration.java:46 opens a raw OkHttp WebSocket in onCreate. Missing that permission alone throws a SecurityException on a real device. Even granted, the target is ws:// (not wss://), and Android blocks cleartext traffic by default since API 28 unless a network security config explicitly allows it — which is also absent here. See section 04.

No error handling on PDF load failures

Medium

The PDFView builder chain in PDFviewer.java:42-49 registers .enableAnnotationRendering(), a scroll handle, antialiasing — but no .onError() or .onPageError() callback. A bad filename (like the BBA bug above) or a corrupt asset fails silently, with nothing but a Logcat line from inside the library.

Deprecated immersive flags, neutralized by enforced edge-to-edge

High

Every Activity's onWindowFocusChanged (for example MainActivity.java:101-112) sets SYSTEM_UI_FLAG_IMMERSIVE_STICKY, _FULLSCREEN, _HIDE_NAVIGATION and friends — all deprecated since API 30. Once this app targets API 35+ (which Google Play now requires), the OS enforces edge-to-edge display regardless of these flags, and un-migrated screens risk content sliding behind the status and navigation bars instead of the fullscreen look these flags were trying to achieve.

onBackPressed is deprecated; no predictive-back support

Medium

Used at Courses.java:41, PDFviewer.java:36, and three places in Registration.java (116, 120, 152). Deprecated since API 33 in favor of OnBackPressedCallback / OnBackInvokedCallback; left as-is, the app won't participate in Android's predictive-back gesture animation at all.

new Handler() with no Looper

Medium

MainActivity.java:66, Registration.java:119,151, SplashScreen.java:47 all call the bare Handler() constructor, deprecated since API 30. Needs Handler(Looper.getMainLooper()).

System.exit(0) to close the app

Medium

MainActivity.java:69 calls System.exit(0) after finish(), bypassing the Android lifecycle entirely. The documented, lifecycle-safe call is finishAffinity().

The "no PDF" sentinel is a literal string

Medium

Rather than a nullable field or simply omitting a button, "this course has no third-year syllabus" is encoded as the string "0":

// Courses.java:189-194
if(myFyPDF.contentEquals("0")) {
    openPDFButton1.setVisibility(View.INVISIBLE);
    openPDFButton1.setClickable(false);
    openPDFButton1.setEnabled(false);
    animationView.playAnimation();
}

Repeated three times per course, twelve times over, at Courses.java:93-125,177-194.

"gray" is 50% translucent black, not gray

Low

<color name="gray">#80000000</color> (colors.xml:10) is an ARGB value with 50% alpha, not a solid gray. It's used as a solid-looking background in activity_p_d_f_viewer.xml and as text color in the splash screen — in both cases it silently composites with whatever sits behind it rather than rendering as the flat gray its name implies.

MBA fee text doesn't match its peer programs

Low

Courses.java:124 lists MBA at "17,900.0 Rs./Year" while every other postgraduate program (all five M.Sc. tracks) charges "29,900.0 Rs./Year." Worth confirming with whoever owns the fee data before carrying it forward.

Security findings

The attack surface here is small — one Activity talks to a network at all — but what it does is worth treating seriously, because it's handling real personally identifiable information.

FindingWhy it mattersFix direction
Critical
PII sent in cleartext, no auth		 Full name, birth date, blood group, phone numbers, and home address are joined into one string and sent unencrypted with no authentication token of any kind. Move to https:// / wss:// with TLS, add a real auth mechanism, and never point client code at an ad-hoc LAN address.
Medium
Unescaped delimiter protocol		 A course name, address, or any field containing a literal $ desynchronizes every field after it, with no validation anywhere in the chain. Replace with a typed serialization format (JSON) over a documented API contract.
Medium
allowBackup="true", lint suppressed		 AndroidManifest.xml:6,13 enables full app-data backup and explicitly silences the lint warning about it (tools:ignore="AllowBackup"), rather than deciding the question. Set allowBackup="false", or scope a real backup_descriptor.xml rule set instead of suppressing the check.
Low
No network security config		 Nothing in res/xml constrains which hosts may be reached in cleartext or pins certificates, because no such file exists yet. Add one once a real backend exists; default to HTTPS-only.
Info
ProGuard rules are the stock template		 proguard-rules.pro is 100% comments — harmless today since nothing needs reflection, but a JSON serializer or DI framework introduced later will likely need explicit keep rules. Revisit when Phase 6 (section 15) introduces new libraries.
09

Performance & efficiency overhead

Nothing here is dramatic at the app's current size, but several of these compound as soon as the course catalog or asset library grows.

High 12 MB of bundled PDFs

36 syllabus PDFs (largest 1.1 MB) make up 75% of this 16 MB repository. Every install carries all 36 whether the user ever opens one or not — a candidate for on-demand delivery or a lightweight backend fetch with local caching.

Low 360 KB of dead weight

res/raw/programmerx.json is a Lottie animation never referenced by any layout or Java file in this repository — confirmed by a repo-wide search. Pure bloat, shipped in every build.

Low Redundant per-screen flag

All five Activities re-set FLAG_HARDWARE_ACCELERATED in onCreate. Hardware acceleration has been the OS default since API 14; this is five identical no-op lines to maintain.

Medium Eager view inflation

The course grid is six stacked ScrollView-nested LinearLayout rows, inflating all 12 CardViews (three children each) up front. Fine at 12 items; the wrong pattern to extend if more programs are ever added.

Low Four autoplaying animations

get_in_touch, tutorials_online, and caution_anim Lottie files autoplay on load across the app's five screens — a continuous decorative CPU/GPU cost worth gating on visibility or interaction instead.

Medium Splash screen double-draws itself

SplashScreen.java:47-52 is a full Activity with a hardcoded 3000 ms delay. On API 31+, the OS already shows its own system splash before this Activity even draws — users see two splash screens back to back. The androidx.core SplashScreen API replaces this pattern entirely.

External calls & data inventory

The entire external-facing surface of this app, in full:

One outbound connection exists in the whole codebase: the raw WebSocket to ws://192.168.2.5:9999 in Registration.java. There is no REST/HTTP client, no analytics SDK, no crash reporter, no ads SDK, and no cloud backend of any kind.

That cuts both ways. The attack surface is genuinely small — there's very little third-party code with network access to audit. But it also means the app's one data-collecting feature has never had a real destination to send data to. Modernizing "safely and efficiently" here isn't just a security exercise; it's also a product decision about what backend, if any, this feature should finally have. See Open decisions.

13

Library replacement plan

Every one of the three dead dependencies has a path that reproduces today's visible behavior exactly.

Animations — daimajia YoYo

Every effect in use (Shake, FadeIn, FadeInUp) is a handful of lines with native ObjectAnimator / ViewPropertyAnimator. Zero dependency, identical motion.

Dialogs — DialogPlus

The app already builds its exit and confirm dialogs with a plain android.app.Dialog (exit_alert_dialog.xml) — only the course popup uses DialogPlus. Bring the popup in line with the pattern the rest of the app already uses: a Dialog/DialogFragment or Material BottomSheetDialog, styled identically.

PDF viewer — barteksc android-pdf-viewer

Two viable paths: the official androidx.pdf PdfViewerFragment (real Jetpack library, but still 1.0.0-alpha19 — risky for production today), or a small custom view over the platform's own android.graphics.pdf.PdfRenderer (stable since API 21, zero third-party dependency, full control over styling). Recommended: build the native PdfRenderer wrapper now; revisit androidx.pdf once it reaches stable.

Registration transport — raw OkHttp WebSocket

Not a library swap so much as a design decision — see Open decisions. Whatever is chosen, OkHttp itself (bumped to 5.5.0) is a fine transport for either REST or WebSocket, just not against a hardcoded LAN IP.

16

Open decisions

Four questions only you can answer — each shapes a later phase above, but none blocks starting at Phase 0.

What should "Register" actually do?

Options range from a real REST/TLS backend you own, to a hosted BaaS (Firebase/Supabase-style), to something as minimal as an email or share-intent handoff to admissions staff until a backend exists.

Where should the minSdk floor sit?

Today's 19 (KitKat) maximizes reach; 24+ is far easier to maintain and is where current AndroidX libraries are trending. Worth checking your actual install base in Play Console before deciding, if you have prior data.

Views + ViewBinding, or a jump to Jetpack Compose?

Incremental modernization within the existing view system is the lower-risk path and matches "same look and feel" most literally. Compose is where Google is investing (Material's Views library is now maintenance-mode) but is the bigger rewrite.

Who owns course & fee data going forward?

Today, changing a single fee requires a new APK release. Worth deciding whether that stays true, or whether course metadata moves to something editable without a store release.
