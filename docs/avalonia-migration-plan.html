00

Executive summary

This is a different kind of project than the companion audit. That document modernized an existing Android app in place. This one plans a rewrite: the same six screens, the same navigation, the same Material look, rebuilt from zero in C# and XAML so one codebase can also run on Windows, macOS, and iOS — platforms the current Java app has never touched.

The timing is genuinely reasonable. Avalonia 12 (April 2026) explicitly targets .NET 10 and SkiaSharp 3.0, and its release notes describe mobile being elevated to "first-class status," with Android startup time dropping from 1,960 ms to 460 ms under NativeAOT and idle CPU use falling 20x. Avalonia 12.1 (July 2026) followed with a native Wayland backend, mobile haptics/sound, and the framework's first Software Bill of Materials for supply-chain compliance. This is a framework investing seriously in the exact four platforms you named, on the exact .NET version you asked for.

The honest framing: nothing in this document is a migration of existing code — there is no C# in this repository today. Every screen, view model, and package choice below is a fresh build that has to reproduce what modernization-audit.html already catalogued: the same 12-course catalog, the same syllabus PDFs, the same registration form, the same Material colors pulled from colors.xml. Budget for a rewrite, not a port.

Two platform-specific realities shape the plan more than anything technical: iOS requires a Mac with Xcode to build and sign, full ahead-of-time compilation (Apple disallows JIT), and a $99/year Apple Developer account — and since macOS is also one of your four targets, that Mac and that account serve both platforms at once. Android, by contrast, lands almost exactly where the current app already sits: net10.0-android defaults to API 36 in .NET 10, which is precisely the API level Google Play now mandates — the same requirement the companion audit flagged for the existing app.

PDF rendering — three real options

AvaloniaPdfViewer (PDFium + SkiaSharp) is the most direct fit but is a small, pre-release personal project (0.0.2-pre on NuGet) — the same maturity caution the companion audit raised about the current Android PDF library. PdfForge.Avalonia explicitly doesn't support Windows or macOS, ruling it out for this platform set. Avalonia Pro (the commercial control pack) ships a "Document viewer" control, which sidesteps this problem entirely if a paid license fits the budget. Recommended default: build a thin custom control over a well-maintained low-level PDFium wrapper, same judgment as recommending a native PdfRenderer wrapper on the Android side.

Android and iOS aren't separate NuGet packages

A direct NuGet search for Avalonia.Android / Avalonia.iOS turns up nothing by design — mobile support arrives through the installed .NET workload (dotnet workload install android ios) plus the platform's own TargetFramework moniker (net10.0-android, net10.0-ios), the same mechanism .NET MAUI uses. The platform head project just references the ordinary Avalonia package; the workload supplies the rest.

07

Platform-specific realities

What actually changes about how you work, once the target list includes Apple platforms.

iOS mandates full ahead-of-time compilation

Critical

Apple disallows JIT compilation for third-party apps on iOS, which has always meant .NET's iOS target compiles fully ahead-of-time rather than JITing like a normal .NET app. This isn't an Avalonia limitation — it's an iOS platform rule that constrains any reflection-heavy code (some serializers, some DI containers) and needs to be kept in mind when choosing packages for the shared core project.

Mobile is Avalonia's youngest target

Immature

Mobile uses the same rendering engine and tooling as desktop, but the third-party control ecosystem is shallower on phones than on desktop. Concretely, this shows up exactly where you'd expect: the PDF viewer situation above is the one place in this plan without a clearly mature, widely-used answer.

Wayland is real now, but opt-in

Info

Avalonia 12.1 graduated native Wayland support out of preview, but it's not yet the default Linux backend — it requires an explicit UseWayland() call. Not on your platform list today, but worth knowing Linux desktop support exists essentially for free if it's ever wanted later.

Apple's yearly SDK treadmill

High

App Store submissions currently require Xcode 26 and the iOS 26 SDK. Historically Apple raises this bar roughly once a year. Shipping on iOS means budgeting time, not just once at launch, for keeping the build Mac's Xcode and SDK current indefinitely.

Android lands almost exactly where you are today

Low

net10.0-android defaults to targeting API 36 — the same Android 16 baseline the companion audit already identified as Google Play's current mandatory requirement for the existing Java app. No extra work here beyond what Path A already needed.

11

Open decisions

One is carried straight over from the companion audit; the rest are specific to building on this stack.

What should "Register" actually do? Carried over

Unchanged by the rewrite — the hardcoded LAN WebSocket from the Java app still has no real destination. Same options as before: a real REST/TLS backend, a hosted BaaS, or a minimal handoff until a backend exists.

Who owns the Apple Developer account?

A $99/year recurring cost and a Mac that needs its Xcode kept current — needs a named owner before Phase 6.

Buy the PDF control, or build it?

Avalonia Pro's commercial document viewer removes section 06's one open spike, at a license cost. Worth pricing out against the engineering time to build and maintain a custom PDFium-based control.

CommunityToolkit.Mvvm, or ReactiveUI?

This plan recommends CommunityToolkit.Mvvm for its simplicity, but ReactiveUI is Avalonia's more traditional default and may suit the team better if there's prior Rx experience.

Any value in the free extra platforms?

Linux desktop and Windows on Arm come essentially for free once Core is built (section 10, Phase 7) — worth deciding now whether that's worth even a small amount of extra testing.
