Executive summary

Same premise as the Avalonia plan: a from-scratch rewrite in C#, one shared codebase, targeting Windows x64, macOS arm64, iOS arm64, and Android arm64, reproducing what the companion audit catalogued about the current Java app. The difference is entirely in the framework underneath.

Uno Platform's XAML is WinUI 3-compatible — on Windows, a Uno app is a real WinUI 3/WinAppSDK app, not an abstraction over one. It ships two first-party pieces this project cares about directly: Uno.Themes gives you Material, Fluent, and Cupertino design systems out of the box, and Uno.WinUI.Lottie plays the app's existing Lottie JSON files with an officially maintained package rather than a community add-on. Both close gaps the Avalonia plan had to fill with third-party or incubating packages.

.NET 10 has been Uno's stable, recommended runtime since version 6.4 (November 2025), and the current Uno.Sdk meta-package sits at 6.7.22 (3 September 2026) — current, actively maintained, squarely on the version you asked to build against.

One detail specific to this project: Uno Platform publishes a formal "Agentic Skills" system with explicit, named support for Claude Code — the exact tool building this plan — alongside GitHub Copilot, Codex, Cursor, Cline, and Aider. That's a concrete, practical fit for a team leaning on AI-assisted development, not a marketing footnote.

Section 02 carries the full head-to-head against Avalonia and a direct recommendation. Short version: reasonable case for either, with Uno edging ahead here on first-party theming/animation and AI tooling fit, at the cost of a larger API surface to learn.

You asked directly which one is better for this project. Here's the reasoning, not just a table.

Performance figures in this row come from each project's own published benchmarks, not independent third-party testing — directionally informative, not a precise head-to-head.

Recommendation: Uno Platform, with a clear-eyed caveat

For this specific project, Uno Platform is the better fit. The deciding factors aren't exotic: this app's whole constraint is "preserve the Material look and the existing Lottie animations with minimal risk," and Uno answers both with first-party, officially maintained packages instead of the community/incubating packages Avalonia needs for the same job. Add the explicit Claude Code tooling support — directly relevant to how this project is actually being built — and the case tips further.

The honest tradeoff: Uno's XAML is the full WinUI 3 surface, inherited from a much larger, older API than Avalonia's deliberately-slimmed dialect. For a team with zero prior XAML experience, that's a real, larger ramp-up cost, not a footnote. If minimizing time-to-first-screen matters more than the theming/animation/tooling advantages above, Avalonia remains a perfectly credible choice — nothing in this document found it lacking, only smaller in scope.

Bottom line: pick Uno Platform if the team can absorb a larger initial API surface in exchange for first-party parity on the two things this app visually depends on most. Pick Avalonia if the priority is the fastest, lowest-friction path to a working cross-platform app and the community packages it needs are an acceptable risk.

PDF rendering — the one gap this framework doesn't close either

Uno has no built-in Windows.Data.Pdf-equivalent control (there's an open feature request upstream). The practical path is Uno's first-party, all-platform WebView2 control hosting a bundled PDF.js viewer — a genuinely different mechanism than Avalonia's PDFium+Skia approach, not obviously better or worse, just a different spike to run in Phase 3. A commercial option (e.g. Telerik's PDF Viewer, embeddable via MAUI interop on supported platforms) exists if a paid control is preferred over building one.

Claude Code integration, concretely

Uno's "Agentic Skills" install as a plugin into an AI assistant and auto-activate by context, covering MVUX patterns, navigation, Toolkit controls, theming, and testing. For a project already being scoped and planned through Claude Code, this is a direct, usable advantage during Phase 0–2 scaffolding, not a hypothetical one.

07

Platform realities

What's specific to building on Uno, once you're past the account/hardware requirements every cross-platform .NET UI stack shares.

Windows is the real thing, not an emulation

Advantage

Because Uno's XAML is WinUI 3-compatible, the Windows build of this app runs as an actual WinAppSDK application. Any WinUI-specific library, sample, or Microsoft documentation applies directly — there's no translation layer to reason about on that one platform.

The WinUI surface is large

High

The flip side of the above: Uno inherits the full WinUI 3 API, which carries more legacy surface area (and more ways to do the same thing) than Avalonia's deliberately trimmed dialect. Budget real ramp-up time in Phase 0 if the team has no prior WPF/UWP/WinUI exposure.

Two rendering modes, one extra decision

Medium

Uno can render everything through Skia uniformly, or use each platform's native controls where available. Either is valid; picking one early (and documenting why) avoids the team drifting between both without noticing.

NativeAOT gains are uneven across platforms

Medium

Android and Linux see the biggest wins (roughly 60%+ faster startup on Uno's own benchmark app); iOS sees the smallest (21%) and needs the most care around reflection-dependent code. Don't assume a uniform payoff across all four targets.

i18n depth is a genuine extra, if ever needed

Advantage

Uno 6.6 added runtime IME composition (Chinese/Japanese/Korean input), Unicode-correct RTL handling, and automatic font fallback across all six platforms it supports. The current app has zero localization (a smell the original audit flagged) — if a Marathi or Hindi version is ever wanted for this Latur-based college, this removes a real chunk of that future work before it starts.

Open decisions

One carried across all three documents; the rest specific to this stack.

What should "Register" actually do? Carried over

Unchanged by which framework you pick — still needs a real backend decision, same options as both prior documents.

Skia-everywhere, or native controls per platform?

Uno allows either. Skia-everywhere keeps the mental model closest to the Avalonia plan if you want the two to stay easy to compare; native-per-platform trades that consistency for a more truly-native feel on each OS.

MVUX, or plain MVVM?

Uno's newer reactive MVUX pattern is built for exactly this kind of list-driven, state-heavy screen (the course catalog especially), but plain CommunityToolkit.Mvvm-style MVVM works fine at this app's scale and keeps the pattern identical to the Avalonia plan.

Is Uno Platform Studio worth licensing?

Not required to ship, but Hot Design's live visual editing and the Select-and-Prompt AI workflow could meaningfully speed up Phases 1–4. Worth a trial during Phase 0 before deciding.

Uno or Avalonia — final call?

Section 02 has the reasoning; this project's answer is Uno, on the strength of first-party theming/animation and the Claude Code tooling fit, provided the team accepts the larger WinUI learning curve that comes with it.
